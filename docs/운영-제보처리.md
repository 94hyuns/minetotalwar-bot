# 운영: 제보 처리 절차 (BUG_MODE=auto)

설계 §33 "제보 처리 루프"를 Claude Code 세션이 그대로 따라 할 수 있게 쓴 운영 절차서다. 디스코드 봇(`discord-bot/`)이 #버그제보 글을 GitHub 이슈로 옮겨 두면, 이 문서를 읽은 세션이 **30분마다** 열린 버그 이슈를 가져가 재현 → 수정 → 배포 → 이슈 닫기까지 한다. 스레드 알림·중계는 봇이 알아서 한다(이슈 댓글 ↔ 스레드, 라벨 → 상태 한 줄, 닫힘 → "수정됨 v1.0.xx" + 스레드 잠금).

- 켜는 법: 모드 저장소 폴더에서 Claude Code 를 열고 이 문서를 읽게 한 뒤 `/loop 30m 열린 버그 이슈 처리`.
- 아래 `<…>` 는 서버마다 다른 값이다. 괄호 안은 우리 서버 값.
  - `<이슈 저장소>` (94hyuns/minetotalwar-bot)
  - `<서버 ssh 별칭>` (ubuntu-server)
  - `<서버 폴더>` (~/minetotalwar)
  - `<서버 tmux 세션>` (mtw)
  - `<모드팩 저장소>` (C:\Users\vkghk\minetotalwar-pack)
  - `<export 폴더>` (~/minetotalwar/export)
- **건의는 자동 처리하지 않는다.** 건의 이슈는 건드리지 말 것(운영자가 "건의 리스트업"을 요청할 때만 정리해서 보여 준다).

## 라벨 규약

| 라벨 | 뜻 | 누가 붙이나 | 스레드에 보이는 것 |
|---|---|---|---|
| `버그` | 버그 제보 | 봇(접수 때) | "접수 #번호 — 자동 처리 중" |
| `건의` | 건의 | 봇(접수 때) | "접수 #번호" |
| `확인중` | 세션이 가져가 처리 중 | 세션 | "확인 중" |
| `보류` | 재현 불가·설계 판단 필요 — 운영자 답 대기 | 세션 | "보류 (관리자 확인 필요)" |
| `상류` | 모드 자체 버그 — 공개 이슈 저장소로 넘김 | 운영자 | "상류 저장소에 올렸습니다: …" |
| `v1.0.xx` (선택) | 고친 버전 | 세션 | 닫힘 알림의 버전 |
| (닫힘) | 처리 끝 | 세션 | "수정됨 v1.0.xx" 또는 "처리됨", 스레드 잠금 |

- #버그제보 스레드는 기본(`BUG_PRIVATE=true`) 비공개라 제보자와 운영자만 본다. 이슈는 공개 저장소에 그대로 공개된다.
- 이슈 댓글은 전부 제보 스레드로 옮겨진다(제보자가 본다). 운영 메모는 댓글로 남기지 말 것.
- 스레드의 제보자 답글은 이슈 댓글 "**이름**: 내용" 으로 온다(끝에 숨은 표식 `<!-- from-discord -->`).

## 30분마다 할 일

### 1. 가져오기

```bash
gh issue list -R <이슈 저장소> --state open --label 버그 --json number,title,labels,createdAt
```

- `확인중`·`보류` 라벨이 **없는** 것만, 오래된 순으로 **한 번에 하나**.
- 없으면 끝. (이미 `확인중` 인 이슈에 제보자 답글이 새로 달렸으면 그걸 먼저 이어서 본다.)

### 2. 착수 표시

```bash
gh issue edit <번호> -R <이슈 저장소> --add-label 확인중
gh issue comment <번호> -R <이슈 저장소> --body "확인 시작"
```

### 3. 원인 찾기

- 이슈 본문·첨부·스레드 답글을 읽는다. 정보가 모자라면 **재현 질문을 이슈 댓글로** 남긴다(스레드로 간다). 답을 기다리는 동안 다음 이슈로 넘어가도 된다.
- 운영 로그: `ssh <서버 ssh 별칭> "tail -n 500 <서버 폴더>/logs/latest.log"` (오류·스택트레이스, 제보 시각 근처).
- 저장 파일이 필요하면 `tools/nbt.py` 로 읽기(운영 월드는 **읽기만**).
- 코드에서 해당 기능을 찾는다(`docs/설계.md` 의 해당 절도 확인 — 설계대로인데 제보자가 버그로 여긴 거면 4번이 아니라 6번 "보류").

### 4. 재현·수정·확인 (개발 서버)

- 개발 서버와 클라 둘 띄우기: `sh tools/restart_dev.sh` (Git Bash, "ready" 가 나오면 준비됨).
- 명령 넣기: `python tools/rcon.py "<명령>"` (예: `mtw gold 1000`, `give Dev1 …`, `tp Dev1 …`).
- **고치기 전에 재현**하고, 고친 뒤 같은 절차로 **안 나는 것을 확인**한다. 빌드만 된 것은 확인이 아니다.
- 수정은 그 버그만 좁게. 커밋 메시지 첫 줄은 플레이어가 읽어도 알 수 있게 쓴다(패치노트로 그대로 나감). 커밋에 `Fixes #<번호>` 를 넣지 않는다(닫기는 배포 뒤 9번에서).

### 5. 배포 여부 판단 (보호장치)

다음을 **모두** 만족할 때만 배포한다. 하나라도 아니면 커밋만 해 두고 다음 주기에 다시 본다.

1. 개발 서버에서 **확인된** 수정만 들어간다.
2. **한 시간에 한 번**만 배포한다. 그 사이 고친 것은 묶어서 다음 배포에.
3. 수치·규칙이 바뀌는 수정(설계 변경)이 아니다 → 그런 건 6번.
4. 운영 상태가 조용하다:
   ```bash
   ssh <서버 ssh 별칭> "cat <export 폴더>/status.json"
   ```
   - `invasion` 이 `null` 이 아니면(침공 진군 중) **미룬다**.
   - 전쟁 중인 세력원이 접속해 있으면 **미룬다**. status.json 의 `war_online` 이 true 면 그 상태다(`war` = 전쟁 중인 세력이 하나라도 있음).
   - `generated_at` 이 3분 넘게 지났으면 서버가 꺼져 있거나 멈춘 것 — 배포하지 말고 운영자에게 알린다.

### 6. 보류 (재현 불가·설계 판단 필요)

```bash
gh issue edit <번호> -R <이슈 저장소> --remove-label 확인중 --add-label 보류
gh issue comment <번호> -R <이슈 저장소> --body "<운영자에게 묻는 질문 — 무엇을 정해야 하는지, 선택지>"
```

- 이 댓글도 스레드로 간다. 제보자가 봐도 되는 말로 쓴다.
- 그다음 이슈로 넘어간다. `보류` 이슈는 운영자가 라벨을 뗄 때까지 다시 가져오지 않는다.

### 7. 재시작 5분 예고

```bash
ssh <서버 ssh 별칭> "tmux send-keys -t <서버 tmux 세션> 'tellraw @a {\"text\":\"[서버] v1.0.xx 배포 — 5분 뒤 재시작합니다\",\"color\":\"gold\"}' Enter"
```

- #서버공지 에도 같은 내용: 웹훅으로 `{"content": "v1.0.xx 배포 — 5분 뒤 재시작"}` POST (웹훅 주소는 모드 서버 설정 `config/minetotalwar-discord.properties` 의 `webhook.notice` 또는 배포 PC 의 웹훅 파일).
- 5분 기다리는 동안 5번 4)를 한 번 더 확인한다(그사이 침공이 시작됐으면 취소하고 "재시작 연기" 공지).

### 8. 배포 + 운영 재시작

1. 버전 올리기: `gradle.properties` 의 `mod_version` → 커밋.
2. 빌드: `./gradlew build`.
3. 모드팩 릴리스: `<모드팩 저장소>` 에서 `.\tools\release.ps1 -Version <버전> -Jar <모드 저장소>\build\libs\<jar>` (패치노트가 #서버공지 로 나간다).
4. 운영 재시작 (start.sh 가 켤 때마다 모드팩 최신 jar 를 받는다):
   ```bash
   ssh <서버 ssh 별칭> "tmux send-keys -t <서버 tmux 세션> stop Enter"
   # 자바 프로세스가 끝날 때까지 확인
   ssh <서버 ssh 별칭> "pgrep -f '^java .*fabric-server-launch' || echo stopped"
   ssh <서버 ssh 별칭> "tmux new-session -d -s <서버 tmux 세션> -c <서버 폴더> ./start.sh"
   # 로그에 Done 이 뜨는지, mods 에 새 버전이 들어왔는지
   ssh <서버 ssh 별칭> "grep -E 'Done \(|Exception' <서버 폴더>/logs/latest.log | tail -n 5"
   ```
5. 기동 실패면 즉시 운영자에게 알리고, 다른 배포는 하지 않는다. (`/롤백` 은 아직 없음 — start.sh 가 모드팩 최신 jar 로 다시 동기화하므로 jar 만 되돌리면 덮어써진다. 되돌리려면 모드팩을 이전 버전으로 다시 릴리스해야 한다.)

### 9. 이슈 닫기

```bash
gh issue edit <번호> -R <이슈 저장소> --remove-label 확인중 --add-label v1.0.xx   # 라벨은 선택
gh issue close <번호> -R <이슈 저장소> --comment "수정됨 v1.0.xx"
```

- 봇이 스레드에 "수정됨 v1.0.xx" 를 올리고 스레드를 잠근다.
- 묶어서 배포한 이슈는 각각 닫는다.

## 하지 말 것

- 운영 월드 파일을 직접 고치거나 지우지 않는다(백업·리셋은 운영자 결정).
- 운영 서버에서 개발용 `/mtw` 명령으로 문제를 "덮지" 않는다(원인을 고친다). 꼭 필요한 복구(골드 지급 등)는 운영자에게 묻고 한다.
- 한 이슈에 여러 기능 수정을 섞지 않는다. 다른 문제를 발견하면 따로 적어 운영자에게 알린다.
- 건의 이슈는 처리하지 않는다.

## 세션 깨우기 (새 버그 이슈가 생기면)

30분마다 도는 반복 작업 대신, **이슈 감시 스크립트**가 1분마다 GitHub 를 보고 새 `버그` 이슈가 생기면 Claude Code 를 한 번 실행해 이 문서대로 처리하게 한다(감시 자체는 토큰을 쓰지 않음).

```
powershell -ExecutionPolicy Bypass -File tools\issue_watch.ps1
```

- 모드 저장소 폴더가 있는 PC 에서 켜 둔다(빌드·개발 서버·release.ps1·운영 ssh 가 되는 곳). PC 가 꺼져 있으면 다음에 켤 때 밀린 이슈를 처리한다.
- `확인중`·`보류` 라벨이 붙은 이슈와 이미 처리한 번호(`tools/.issue_watch.json`)는 건너뛴다. 다시 시키려면 그 파일에서 번호를 지운다.
- 처리 기록은 `tools/logs/issue-<번호>.log`.
- **권한**: 기본(`--permission-mode acceptEdits`)은 파일 편집만 자동 허용이라 빌드·ssh·배포 명령에서 멈춘다. 무엇을 자동 허용할지는 운영자가 정해 `-ClaudeArgs` 로 넘기거나 저장소 `.claude/settings.json` 의 허용 목록에 넣는다.
- Claude Code 디스코드 채널 플러그인(Channels)으로 깨우는 방법은 쓸 수 없다 — 플러그인이 봇·웹훅이 보낸 메시지를 전부 버린다(`server.ts`: `if (msg.author.bot) return`).
